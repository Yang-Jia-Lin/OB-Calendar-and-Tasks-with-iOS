# 产品需求与实施顺序

基线：2026-10-31 用户最新确认。本文是需求主文档；架构见 [架构设计](2-架构设计.md)，已有成果见 [开发日志](开发日志.md)。目标产品与当前 0.2.14 插件分别描述，不能混作已完成能力。

## 1. 已确认的产品方向

| 决定 | 当前约束 |
| --- | --- |
| 电脑为记录主力 | 必须有独立桌面 APP，OB 未打开时仍可使用；它是目标产品，不再列为可选附属工具 |
| 桌面展示保持轻量 | 以待办和核心摘要为方向，不要求展示整月全部日程／记录；具体布局、范围和摘要内容待用户进一步考虑 |
| OB 为科研执行主阵地 | 在课题、任务和 Components 首页按钮中计时；插件主页面继续提供总览、记录编辑与异常处理 |
| 下一步先完善 OB／Components | 先统一科研任务关联和计时入口，再推进 iCloud 任务接入及桌面端；不先搭完整桌面界面 |
| 云端业务数据统一 iCloud | 日程／实际记录进入 iCloud 日历，行动任务进入真正的 iCloud 提醒事项，不新增任务云或自建同步服务器 |
| 日期语义分开 | 安排日期表示准备哪天处理，截止日期表示最迟何时完成；两者独立、均可为空 |
| 保留“待安排” | 无安排日期的任务集中收纳，不每天全部放进日期栏 |
| iPad 复用原生应用 | 继续补记、安排、查看和处理提醒事项，不开发替代原生日历／提醒事项的 iPad 客户端 |
| Android 暂缓 | 后续只读即可，不作为本轮或桌面首版的门槛 |

“全部 iCloud”指任务、日程和已保存记录的统一业务来源。OB 笔记正文仍由用户原有笔记管理方式保存；本地缓存、未同步草稿、恢复日志和凭据保护仍有必要，不引入第二份云端主库。共享代码不代表自动共享正在运行的计时器。

## 2. 四类业务内容

| 内容 | 典型动作 | 保存与显示 |
| --- | --- | --- |
| 生活补记 | 活动结束后，填标题／分类／起止时间并保存 | 直接写实际记录，不要求先建任务或启动计时 |
| 科研行动 | 从课题任务启动、暂停／继续、结束计时 | 一项任务可以对应多次工时；结束计时不默认等于任务完成 |
| 未来日程 | 安排会议、预约或具体工作时段 | 写日程；进入过去也不能自动认定已经实际执行 |
| 周期事务 | 例如每周六交周报，到对应周期日进入当天视图 | 维护重复规则与当前一轮状态；完成本轮不结束整个系列 |

课题、长期方向和可执行任务分开：课题保留研究背景与笔记；具体行动可计时；实际工时记录执行结果。科研分类用于选择写入日历，课题关联用于返回研究上下文，两者不是同一个字段。

计划与实际即使显示在同一天，也要可区分，避免把过去的未执行计划当实际工时，或把计划和对应实际记录重复计入摘要。是否保留计划对照及具体视觉形式尚未确定。

## 3. 任务日期与当天显示

- `scheduledDay`：准备执行的本地日历日期，不是时间点；不因时区变化自动平移到另一天。
- `due`：无截止、某日截止、某时刻截止三种语义；日期截止保留浮动日期，时刻截止保留 UTC 时间点和显示时区。
- 设置截止日期不自动填安排日期；安排到某天也不自动改截止日期。
- 某日任务栏按安排日期展示；截止提示另显示，不把仅有截止日期的任务偷偷当作已安排。是否增加“当日到期”分组由桌面设计再定。
- 无安排日期的任务进入“待安排”，即使有截止日期也不自动变成每天出现的任务。
- 如果用户给任务安排了具体时间，才另建未来日程并关联任务；实际计时仍单独记录。

显示日期不等于推送提醒，通知策略沿用原生能力，本轮不承诺另建通知系统。

例：周报可以周五安排处理、周六截止。论文阅读可以周二安排、无硬性截止。尚未决定何时处理的论文任务留在待安排，不复制进每天。

周期事务按其有效周期日在当天出现；下一轮何时可操作、漏做后保留／跳过／延期、是否提前显示，均尚未确认。不得默认删除未完成实例，也不把“漏做区域”建议当成用户已确认要求。

## 4. 各端职责与流程

### 电脑桌面 APP

承担日常全局入口：待办／待安排、核心摘要、快速生活补记和未来安排。任务可出现在对应日期的任务区域，日历事件与任务保持不同实体。历史仍可查询和补记，但不要求常驻界面展示整月历史。

常驻、置顶、桌面嵌入方式、默认日期范围、是否提供完整日历扩展页、摘要指标与具体界面都待定。不得把目前 OB 的 1:2 布局、完整月网格或新的统计模块直接搬成桌面需求。

### OB／Components

课题卡片中的开始按钮引用同一项行动任务；只使用 Components 原生按钮属性开始计时；不在 Markdown 中嵌入控件，不改卡片封面。点击后留在原科研页面，状态和后续控制沿用插件页／命令／状态栏。插件页、命令、状态栏和 Components 共同操作插件内同一会话和队列，不各建任务／计时器。

结束默认可以只记工时；用户明确选择“结束并完成”时才完成该任务或本轮事务。沿用用户已创建的原生按钮属性，只补脚本动作，保留其名称、位置和样式。

### iPad 与手机

iPad 继续使用原生日历／提醒事项，对同一 iCloud 数据操作。生活补记希望电脑、iPad、手机都方便，但本轮优先电脑和现有 iPad 路径；Android 写入不承诺，后续先评估只读。

## 5. 实施顺序与验收

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| P0 本轮文档 | 统一需求、架构、验证边界 | 清除“桌面可选”“科研任务永久分库存储”等冲突表述；已有测试证据不丢失 |
| P1 已实现、待实机验收 | OB／Components 共用科研计时入口 | 一张实际课题卡片能启动已有任务；插件页可暂停／继续同一会话；结束只生成一份工时，不重复建待办，刷新后状态一致 |
| P2 iCloud 任务最小接入 | 普通提醒事项、任务绑定、日期与课题信息持久化 | OB 创建／编辑／完成同一提醒事项；iPad 可核对；不确定提交不重复创建；安排／截止独立往返，旧数据显式迁移；原生复杂字段受保护 |
| P3 必做桌面 APP | 独立运行的轻量任务／摘要入口、补记和安排 | OB 关闭仍能使用；从 iCloud 读取结果；不用在电脑与 iPad 重复录入；具体界面先确认再实现 |
| 周期能力验证与接入 | 当前一轮与下一轮、有效日期显示、完成语义 | 普通任务接口成功不能代替此项。若桌面首版承载周期事务，须先通过该项；未支持期间明确提示，不盲写系列 |
| 后续 | Android 只读等 | 不阻塞 P1—P3，不预建原生端工程 |

P1 可先复用现有 Markdown 任务与 FCR 写日历闭环，属于兼容过渡，不等于 iCloud 待办同步已完成。P2 后目标是提醒事项为唯一任务主记录，OB 表现为科研关联／视图，不长期维护两份独立可写任务。不得自动扫描整个笔记库并全量上传。

## 6. 已确定与待定的界线

已确定：桌面必做、电脑主力、OB 科研／计时、P1 优先、日期分开、待安排、iCloud 统一、iPad 原生、Android 后置。

设计默认：活动计时仍在发起设备恢复；本地日志／草稿确保断网不丢操作；任务与工时通过稳定身份关联。不同设备暂不接力活动计时，不承诺全局计时锁。

待定：桌面布局与摘要、周期漏做政策、安排日期和课题关联在原生提醒事项中的可靠映射、旧 Markdown 的选择迁移方式。待定技术映射必须验证，不能假定 iCloud 提供任意自定义字段。

## 7. P1 当前交付状态（0.2.14）

按用户明确纠正，卡片仅需一个 Components 原生按钮属性。当前沿用用户在“当前”视图创建的按钮，只补运行脚本表达式 `CalendarTaskTimerStart()`；早先加入的 Markdown 计时章节、章节封面与嵌入式控件已撤回。课题与已有任务的绑定保存在插件设置，不写入课题正文。

“视频感知优化”已关联原有未完成待办，其他课题首次点击可选择已有待办。绑定使用源路径与稳定任务 ID，不复制任务，不把课题笔记自身任务列表与计时待办当成相同来源，暂不支持整库任意任务行直接计时。

135 项核心／桥接测试及 77 项浏览器回归通过；本机运行版本、原生按钮、脚本文件识别及嵌入控件清理已只读核对。遵照本轮收窄后的需求，没有点击开始或新增测试工时，实际按钮开始和真实日历往返不写成已验收。P2／P3 不在本轮扩展。
